How to type this app, not just build it

This document exists because the copy is the product. Noop’s whole claim is that it will not overstate what it knows, and that claim lives entirely in sentences. A build can have every hex, radius and curve right and still ship a different product, because someone rewrote no real change as stable, or not enough yet as keep going!, or added an exclamation mark to a line that was deliberately flat.

So this is not a second design spec. spec/00-RULES.md and the eight act specs already carry geometry, tokens, primitives and routes, and they still win on all of that. This document carries the things a coder has to get right that are not geometry: where every string comes from, which strings the app writes itself, and the gates that decide whether a sentence is allowed to exist at all.

Read in this order

  1. spec/00-RULES.md — the twelve things that make a faithful build look cheap. Still the top authority on anything visual.
  2. This document, §1–§3. The copy law, the lift procedure, the honesty gates. Twenty minutes, and it prevents the class of bug that is invisible in review.
  3. spec/10-tokens.md, 20-primitives.md, 30-routes.md — build the fifteen primitives before any screen.
  4. The act spec for the act you are on, alongside §5 of this document for that act’s generated strings.
  5. spec/50-wiring.md for what feeds each bound value, and spec/acts/48-act9-instrument.md for the new act.

1 · The copy law

Twelve rules. Each one is a real defect that has shipped in a health app, and eleven of the twelve are things a well-meaning developer does while trying to be helpful.

1.1 — A static string is a literal, like a hex code

Type it exactly. Do not shorten it to fit, do not sentence-case a lowercase label, do not expand a contraction, do not swap an em dash for a hyphen. If it does not fit your layout, the layout is wrong — the strings were written against 402 pt with the real type scale.

1.2 — Never invent a sentence for a state you have not been given

If your data hits a case the spec does not name, that is a spec gap and it blocks the screen. Do not fill it with Something went wrong. Every state in §6 has a designed sentence; if yours is not there, ask.

1.3 — No exclamation marks, anywhere in the app

Not in a celebration, not in an error, not in an empty state. There are zero in the prototype and that is deliberate.

1.4 — The app never congratulates and never scolds

It reports, and it occasionally says something is worth noticing. Great job! and You missed your goal are both out of voice. The nearest the app comes to praise is naming what happened and its consequence: Eleven weeks inside your own bedtime hour — previous best was three.

1.5 — Second person, present tense, no imperatives unless there is one action

You slept 7h 12m, not Sleep: 7h 12m and not User slept. An imperative is allowed only where the screen offers exactly one thing to do, and then it names the action plainly: Log a few days without it.

1.7 — Uncertainty is stated in the sentence, not in a superscript

Every estimate says it is one, in words, at the end of the screen it appears on. Estimated from resting pulse, recovery after effort and the pace you hold at a given heart rate. It is a direction with an error bar, not a laboratory figure. Do not replace this with an info icon.

1.8 — The app never claims cause

Association only, and the word because is only allowed when the app is describing something you did, not something it inferred. Banned constructions: X caused Y, X improved your Y, because of your late meal. Allowed: On the mornings after a drink, your readiness runs 19% lower than on mornings without one.

1.9 — A refusal is a designed answer, not an error

When the app declines — not enough data, strap off the wrist, a night with a hole in it, a question Svea will not answer — it says what it cannot do, why, and what it can do instead. Three parts, in that order, and never in red.

1.10 — Numbers in copy come from the same call as numbers on screen

A sentence that says down 5 beats beside a chip that says −4 is the worst class of bug in this app, because it destroys the only thing the product sells. Compute once, format twice, from one value.

1.11 — Empty is not zero

0 means measured as none. Absent means not measured, and it renders as — with a reason available. Never print 0 for a missing reading, and never print — for a true zero.

1.12 — Localisation happens once, centrally, or not at all

Do not paraphrase in a locale file. The generated strings in §5 are templates with slots; translate the template, keep the slots, keep the gates. A locale that reads more encouraging than English is a broken locale.

2.2 — Where a string lives inside the file

Each act file has two halves. The template is the markup; the logic class is a single renderVals() that returns everything the template interpolates.

  • A string sitting in the template markup is fixed chrome — a section label, a caption, a footnote. It is static without exception.
  • A string returned from renderVals() as a plain value is static copy held in code, usually because it varies by state. It is still final wording; the branch is what varies, not the words.
  • A string built by concatenation inside renderVals() is formula. Those are the ones this document tabulates in §5, because they are where a build invents its own voice.
  • Anything under a TERMS or T. lookup is schedule vocabulary — §4.

2.3 — The procedure

  1. Open the act file. Search for the screen’s sc-if block: isCharge, isMetric, isAlarm. Everything for that screen is inside it, in visual order.
  2. Copy the strings out in that order into your Swift file. Keep the order — it is the reading order, and reordering cards changes the argument the screen is making.
  3. For every {{ hole }}, find the key in renderVals(). If it is a concatenation, go to §5 and implement the template, not the example output.
  4. Diff your finished screen against the prototype with both on screen. Read the sentences aloud. A misplaced comma in this app is a bug report.

The one thing not to do: screenshot the prototype and transcribe from the image. Every apostrophe in the app is a typographic apostrophe (U+2019), every dash in prose is an em dash with no surrounding spaces, and every minus is U+2212. OCR gets all three wrong, and the result is a build that looks right and is subtly not the product.

5 · The strings the app writes itself

These are the formula strings. Each is a template with slots; the slot is filled from the same value the screen displays (§1.10). Where a template has variants, the variant is chosen by a gate from §3 — never by how the number feels.

5.1 — Trend rows (Act 4 trends)

Four rows, each with four sentence variants. The variant is chosen: short if the window is six weeks; else noise if the change is under threshold; else good or bad by whether the change went the way the signal’s better direction wants. Slots: {d} the absolute change with unit, {m} the change in minutes, {from} the window’s start in words, {inFrom} the same with a preposition.

The blend, exactly

w        = ownNights / (ownNights + 18)          // weight on your own slope
shown    = published × (1 − w) + mine × w
state    = ownNights < 8   → borrowed
           |mine − published| > 3 and ownNights ≥ 40 → disagrees
           ownNights < 40  → blending
           else            → yours
hue      = borrowed #C6CEC9 · blending #AFB9E2 · yours/disagrees #8B99D6
fillWidth= borrowed 6% · blending 48% · disagrees 88% · yours 100%

The numeral takes the hue. That is the treatment doing the work the sentence would otherwise have to do, and it is the reason this engine can answer on day one without lying. If the build cannot hold that distinction, dose-response does not ship.

8 · Per-screen QA

Fourteen checks. A screen is not done until all fourteen pass, and eight of them are about sentences.

  1. Every string matches the prototype character for character — apostrophes, em dashes, minus signs.
  2. No exclamation marks. No banned vocabulary (§1).
  3. Every number in prose comes from the same value as the number in the chart.
  4. Each applicable state from §6 renders, and was viewed on device.
  5. The thin state keeps the row and drops the claim.
  6. The absent state shows —, not 0.
  7. Every refusal has all three parts, and is not red.
  8. Schedule vocabulary switches with the profile answer (§4).
  9. Tracking in points, not ems. Line spacing computed, not guessed.
  10. Borders 0.5 pt with strokeBorder; corners .continuous.
  11. Every tap target ≥ 44 pt. The range control and segmented rows included.
  12. Dynamic Type to XXL without clipping; numerals stay tabular.
  13. Reduce Motion honoured; no animation re-runs on a range change — values interpolate, 220 ms.
  14. The screen has a door from somewhere a user actually stands.

10 · The visual contract

spec/10-tokens.md and swift/NoopSpecTokens.swift remain the authority on the palette, the radius ladder and the tinted-card rule. But that pack predates the work in Acts 6–9, and one of its rules is now wrong. This section is the correction and the additions — every graphic, gradient, blur, curve and measurement introduced since, at the exact value.

Correction to 10-tokens.md §“The one gradient”. It says there are no other gradients in the app; if a card in the build has one, delete it. That was true of Acts 1–5. It is no longer true.

There are now four kinds of gradient, and no others: the orb (unchanged), the body-age aura, the tinted-verdict wash, and the screen-top ambient bloom. All four are written out below. A gradient anywhere else is still a bug — and in particular cards still have none, and neither does any button, chip, row or tab bar.

c · The tinted-verdict wash

linear-gradient(158deg, tint(hue, .16), rgba(46,204,128,.03))
border .5 pt  tintBorder(hue, .30)     radius 24

Used on exactly three things: Act 4’s window verdict, Act 9’s fit card when the fit clears, and Act 8’s reached-milestone card. 158°, not 160° and not 180° — it is the one directional gradient in the app and the angle is shared so the three read as one family. When the state does not clear, the card loses the gradient entirely and becomes a plain #141817 card with a white 8% border. That swap is the honesty gate made visible.

d · The screen-top ambient bloom

position absolute; top −150; left 50%; translateX(−50%)
470 × 410  radius 50%
radial(circle, rgba(HUE,.15–.16), rgba(HUE,0) 70%)   blur 18

One per screen root, in the act’s hue: green in Acts 1–6, lavender in Acts 7 and 9. It is behind everything and it never animates. It is the reason the top of a screen does not look like a black rectangle, and builds that omit it look flat in a way reviewers describe as “cheap” without being able to name.

10.6 — Icons

Every icon in the app is a monochrome mask, not an image and not a multicolour SVG. One 24×24 box, fill: none, stroke-width: 1.7, round cap and join, and the colour comes from the mask’s background — which is how the same glyph is amber in one row and grey in another.

size    17 in a list row · 18–20 in a link row · 19 in the tab bar · 21 centre button
colour  the row's own semantic colour, never a fixed icon grey

In SwiftUI this is a Path in a 24-unit space with .stroke(style: .init(lineWidth: 1.7, lineCap: .round, lineJoin: .round)), scaled with .scaledToFit(), tinted by .foregroundStyle. Do not substitute SF Symbols: the weights do not match at these sizes and the app’s glyph set is deliberately thinner than SF Symbols’ .light.

10.7 — The eight visual traps

  1. A shadow on a card. Cards have none. NoopPanelSurface adds one by default — use NoopSpecCard.
  2. A gradient on a card, button or chip. Only the four in §10.3.
  3. .stroke instead of .strokeBorder. Half the line renders outside the shape, the radius visibly grows, and every edge in the app goes soft at once.
  4. .circular corners. The default. At radius 22–26 the difference is plain.
  5. Tracking in ems. .tracking() takes points. This is the single largest source of drift.
  6. Uniform sparkline colour. The stroke carries the verdict; a screen of identically-coloured sparklines has thrown away the information.
  7. Dimming a whole row to show “unavailable”. The app dims the control to 38 % and leaves the text legible. A greyed row reads as broken; a dimmed segment reads as not-yet.
  8. Rounding a blur or an opacity. blur 4.5 is not blur 5 at these sizes, and .055 is not .06 on a hairline that runs the width of the screen.

How to check yourself. Put the prototype and the build side by side at 402 pt, screenshot both, and difference the images. Everything in §10 was chosen so that a correct build differences to near-black. If a region lights up, the value is in this section — look it up rather than nudging until it looks close, because “looks close” is how a build accumulates the twenty small wrongnesses that add up to a cheaper-feeling product.

Where this document and the prototype disagree on a number, the prototype is right and this has a typo. Where they disagree on a sentence, the prototype is right and it is not a typo — it is the product.
